# Facebook enquiry workspace

Load facebook-enquiries.js/css. SHFacebookEnquiries exports pages:['Facebook enquiries'], render(page,ctx), bind(page,ctx), panel(ctx), bindPanel(ctx). Panel can be inserted in staff Overview or Sales & CRM. Every render/panel/bind/action requires ctx.role==='staff'. Context requires store, leads, escape, save, navigate and toast. save can be synchronous or asynchronous; false/rejection restores previous owned arrays and leads. Shared records require production server authorization in addition to these UI guards.

Storage keys: facebookPosts, facebookEnquiries, facebookCRMLeads and existing leadNotes. No project ID is required; these are SH business-wide sales records. Facebook posts have id, postKey, groupId, facebookPostId, canonical url, title, design, campaign, author/public confirmations and registration timestamp. Enquiries reference the registered post's internal id and canonical postKey, preserve author/originalText, commentId/commentURL/date, optional customer-supplied contacts with provenance, metadata, current follow-up fields and append-only history. Status choices are New interest, Contact details requested, Qualified, Quote preparation and Closed. Marketing consent is explicitly Not recorded.

URL parser permits HTTPS on exact facebook.com, www.facebook.com, m.facebook.com, mbasic.facebook.com and basic.facebook.com hosts. Only /groups/{identifier}/posts/{postId} and /groups/{identifier}/permalink/{postId} paths are accepted. Credentials, nonstandard ports, lookalike hosts, share/profile/private-message paths and ambiguous comment IDs are rejected. Canonical post links strip tracking; comment/reply IDs are stored separately and source links rebuilt. Numeric group IDs are preferred; a public group slug is supported but cannot automatically be resolved to a numeric-ID alias without Facebook access. Users must use matching group identifiers when registering a post and capturing its comments.

Registration requires SH-authorship and public-group confirmations and blocks duplicate canonical post keys. Comments can only reference such registered posts and require confirmation of visible public provenance. Duplicate comment IDs are blocked across URL variants; when either entry lacks a comment ID, normalized post+author+original text detects likely duplicates and returns the existing record reference. Distinct known IDs remain distinct even if two real comments have identical wording. Original text is preserved; normalization is only for the fallback key.

Explicit Create/link CRM action is idempotent by sourceEnquiryId. CRM leads have stable id and sourceEnquiryId plus normal name/region/source/stage/value fields; the same new lead is added to ctx.leads and store.facebookCRMLeads. Root persists and merges remote CRM rows by stable ID/sourceEnquiryId. New opportunity value is zero until SH qualifies it. A provenance note records stable leadId/facebookEnquiryId/sourceEnquiryId and local leadIndex for existing UI compatibility; root remaps indices on cross-device hydration. One enquiry produces one provenance note and CRM-link history event. Follow-up history preserves earlier notes and timestamps.

This workflow is manual. It contains no Facebook API integration, scraping, inbound synchronization, private/third-party post workflow, messaging, automated response or outreach. Optional contact information must have been supplied manually, with source recorded. Contact requested status does not send a message or infer consent.

Validation: `node --check dist/facebook-enquiries.js` and `node scripts/check-facebook-enquiries.cjs`. Checks cover URL safety/canonicalization, required SH/public confirmations, registered-post boundaries, exact and fallback duplicates, role guards, calendar dates, follow-up history, idempotent lead/provenance creation, failed-save rollback and escaped rendering including revalidated stored source links. Integrated browser/server persistence remains the root workspace's responsibility.
